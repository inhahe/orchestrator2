- [x] **5. Faster perceived startup** — three layers of fix:
  1. The `--detach` parent's hardcoded `sleep(2)` was replaced with port-polling that opens the browser the instant the child serves; the page shows `connecting…` while the SDK finishes loading (state marked `connecting` immediately in `start()`).
  2. **Lazy heavy imports.** `import server` used to cost ~1145 ms because it eagerly imported `fastapi` (~350 ms), `uvicorn` (~120 ms) and `sdk_bridge`→`claude_agent_sdk`→`mcp` (~470 ms) at module top. The `--detach` **parent** paid all of that before it even spawned the child (which then paid it *again*) — two sequential ~1.1 s imports = the multi-second delay. Now those modules are imported lazily: routes are declared via a lightweight `@_route`/`@_ws_route` registry and the FastAPI instance is built in `build_app()` (called only by the serving process); `uvicorn` is imported in `main()`; `sdk_bridge` is imported in a deferred task. Result: `import server` is ~185 ms and the parent loads **none** of the heavy modules.
  3. **Deferred SDK bridge.** Building the `SDKBridge` (which imports `claude_agent_sdk` and spawns the Claude CLI) was moved out of the lifespan critical path into `_deferred_bridge_startup()`, scheduled *after* lifespan yields — so uvicorn accepts connections and the page loads immediately. A `_bridge_ready` asyncio.Event guards the brief window where `bridge is None` (the WS handler and picker `/api/resume` await it). *(server.py, sdk_bridge.py)*
  5. **Instant-startup splash + socket handoff.** Root finding: binding/listening on a port is instant (~0.2s); the multi-second startup is entirely `import fastapi` (0.34s) + `import uvicorn` + pydantic + building ~20 routes + uvicorn's asyncio setup — the framework, not the port. A bare stdlib `http.server` listens in **0.23s** vs orchestrator2's **1.4–3.3s**. Fix: `main()` now `_bind_port()`s the socket, then a stdlib pre-server thread (`_serve_splash_until`) `listen()`s on it and serves a lightweight "starting orchestrator2…" splash (whose JS polls `/api/ready`), and the browser is opened at it **immediately** (~0.3–0.5s). fastapi/uvicorn build on the main thread meanwhile; then the splash stops and the **same still-listening socket** is handed to uvicorn (`server.run(sockets=[sock])`). The splash's `/api/ready` poll returns 503 until uvicorn answers 200, then the page `location.replace('/')`s to the real UI (~1.35s). Connections arriving during handoff sit in the kernel backlog (never refused). New `/api/ready` route added. Measured: tab @ ~0.3–0.5s, real UI @ ~1.35s. **Caveat:** rare 10-12s spikes are the *pre-main* Python interpreter+`import server` cost inflating under Windows process-launch overhead (Defender scanning DLLs) / load — that happens before any server (splash or fastapi) can listen, so the splash can't cover it; it's environmental, not a code inefficiency. Replaces the old `_open_when_ready` TCP-poll opener. *(server.py)*
  4. **"Can't connect" regression fix (non-detach path).** The active `orch2.bat` launch is the **non-detach** single-process path (`--open`, no `--detach`). Its browser-opener thread fired `webbrowser.open()` the instant `_server_ready` was set — but that event is set at the end of lifespan **startup**, and uvicorn only calls `listen()` *after* lifespan startup returns. So the browser hit a bound-but-not-listening port → "can't connect". Fixed: after `_server_ready`, `_open_when_ready()` now polls a real TCP `connect()` (matching the `--detach` parent's probe loop) until the port genuinely accepts connections, *then* opens the browser. Measured cold start to actually-listening is ~1.6 s (interpreter ~0.25 s + `import server` ~0.18 s + `build_app()`/fastapi ~0.43 s + uvicorn ~0.06 s + lifespan/listen); the page then shows `connecting…` while the SDK bridge finishes in the background. This ~1.6 s is close to the floor for a fastapi+uvicorn process — going lower would need dropping fastapi for raw Starlette (~0.2 s) or a bigger rearchitecture. *(server.py)*

- [x] **8. Prompt "eaten" while connecting** — a prompt typed while the UI showed "connecting" vanished: not queued, not run. Root cause: `connect()` clears `state.connecting` in its `finally` on **failure** too, so during the retry backoff (and the 45s-timeout hang→retry) the backend had `connecting=False` while the browser still displayed "connecting" (no `status_update` is broadcast on failure, so the frontend's `_isBusy` stayed stale-true). A prompt then hit the WS handler with `connecting=False and busy=False` and routed to the **invisible** `event_queue` instead of the visible `queued_prompts` — where, in a never-succeeds hang, it was never drained. Fixed: `worker_loop`'s connect-retry loop now **re-asserts `state.connecting = True` for the whole backoff window** (and pushes a fresh `status_update` so the browser's `(Ns)` timer stays live), so typed prompts land in the visible queue and are drained on the eventual successful connect. The post-`MAX_CONNECT_ATTEMPTS` give-up path clears `connecting` (so the manual-retry `event_queue.get()` still works), and if prompts are already queued it just keeps retrying (every 30s) rather than making the user re-type. Verified with an end-to-end harness (fail×2 then succeed): the mid-backoff prompt routes to `queued_prompts` and runs. *(sdk_bridge.py — new `_broadcast_status()` helper)*

- [x] **10. Queued prompts survive server restart** — the queued-prompt list already survived a *browser* reload (it's server-side state, re-sent in `panels` on connect), but a full **server restart** lost it. Now the queue is persisted to disk. `state.py` gains a `PersistentDeque(deque)` subclass that fires an `on_change` callback after every mutation (append/pop/clear/etc.); `queued_prompts` is now such a deque. `session.py` gains `queue_file_for_cwd` / `load_persisted_queue` / `save_persisted_queue`, storing the queue as JSON at `<config-dir>/orchestrator2/queues/<sanitized-cwd>.json` (atomic temp-file replace; the file is deleted when the queue empties). `server.py`'s new `_attach_queue_persistence(state, cwd)` loads any saved queue into the fresh state and wires the `on_change` save hook; it's called at both `init_state_from_config` sites (lifespan startup + `_reconfigure`). Verified with a round-trip test. *(state.py, session.py, server.py)*

- [x] **11. `copy_session.py` — graphical TUI to move a session between accounts** — full-screen [Textual](https://textual.textualize.io/) wizard (`python copy_session.py`, no args) that copies a session's JSONL from one `.claude` account to another so a conversation started under one account can be resumed from a different one. Flow: **(1)** pick the source `.claude` dir from an auto-discovered list (scans `~/.claude*` folders with a `projects/` sub-dir, plus `CLAUDE_CONFIG_DIR`; shows session counts) → **(2)** pick a session from a `Tree` **grouped by project directory** (each group labelled with the project's cwd; leaves show date + title + short id, title read from custom-title/ai-title/first user message). Because reading every session's title opens each JSONL (slow for a big account), the session list is scanned in a **worker thread** (`@work(thread=True)`) behind a `LoadingIndicator` + live "Scanning sessions… N/total" count (throttled to ~10 Hz) instead of freezing the UI on click; `scan_sessions` gained an optional `progress(done)` callback for this → **(3)** pick the destination `.claude` dir → **(4)** name the copied session (defaults to the original id). The copy goes to the **same** project-slug sub-path in the destination. If the new name differs from the source id, every top-level `sessionId` field in the JSONL is rewritten to the new id so the copy resumes cleanly; identical name → byte-for-byte copy. Overwrite is guarded by a y/n confirm modal, and a second y/n confirm warns when the chosen name/id already exists **elsewhere** under the destination account (a different project slug) — via the new `sessions_with_id(claude_dir, id)` helper — since duplicate ids make `claude --resume <id>` ambiguous. On success prints the `claude --resume <id>` command. Non-TUI helpers (`discover_claude_dirs`, `scan_sessions`, `copy_session_file`) are import-testable; verified end-to-end with Textual's `Pilot` harness (full wizard, id-rewrite, plain copy, overwrite yes/no). **New dependency: `textual`** (installed via pip; pure-Python, builds on already-present `rich`). *(copy_session.py)*

- [x] **12. `--resume` / `--copy` launch-time TUI picker** — launching orchestrator2 with `--resume` (no id) or the new `--copy` flag now opens the Textual picker in the terminal *before* the server starts, so the user chooses the session to resume from a full-screen UI (grouped by project directory) instead of the in-browser picker. The account is the one selected by the current `CLAUDE_CONFIG_DIR` (set from `--config-dir` / env). **`--resume`** → pick a project+session from the current account; **`--copy`** → a full copy wizard: pick a *source* account + session, a *destination* account, and a *name* for the copy (with the same duplicate-id warning + overwrite guard as the standalone wizard). When the destination is the **current** account the copy is then resumed; when it's a **different** account the copy is made and a `NoticeScreen` explains it won't be resumed here (the server can only resume its own `CLAUDE_CONFIG_DIR`), then the server starts normally. `copy_session.py` gains `current_claude_dir()`, `_same_dir()`, `NoticeScreen`, `LaunchPickerApp(mode, current_dir)` (reusing `ClaudeDirScreen`/`SessionScreen`/`NameScreen`/`ConfirmScreen`), and `pick_session_for_launch(mode) -> {"session_id", "cwd"}`.

  **Resume is cwd-scoped (bug fix).** The CLI only finds a `--resume <id>` session under the *current cwd's* project slug, so picking (or copying-in) a session that belongs to a **different** project than the launch cwd previously failed with a cascade of "SDK connection failed (attempt N/10)" retries (the copied file lived under the source project's slug, not the launch cwd's). Fixed: the picker now also returns the picked session's own `cwd`, and `server.py`'s `main()` **adopts it** (`config.cwd = that cwd`, if the directory still exists) before starting — so the resume resolves under the right project. This applies to both `--resume` (any picked session) and `--copy` (resume-in-current-account case). For `--detach` the child argv now strips any inherited `--cwd` and re-adds the resolved `config.cwd`. `server.py`'s `main()` runs it after the config-dir env is set via `_run_launch_picker(mode)`, which on Windows **always** runs the picker as a **child process** (`copy_session.py --pick <mode> --out <tempfile>`) — never in-process — so the server process never hosts a full-screen Textual app whose terminal teardown could wedge the subsequent uvicorn startup (the earlier "window hanged after selecting a session" symptom). The console for that child is chosen by a new `_console_is_visible()` helper (`GetConsoleWindow` + `IsWindowVisible`): if our own console window is **visible**, the child **shares it** (`creationflags=0`, TUI draws in the current terminal); if our console is **hidden** (the tray_minimizer launch gives the server a real-but-`SW_HIDE`n console, so `isatty()` is true but drawing there is invisible) or **absent** (VS Code "Run"/Output pane, a double-click), the child gets its own **fresh, visible** console via `CREATE_NEW_CONSOLE`. Either way the picker is always something the user can see, while the server itself stays hidden in the tray. The parent waits, then reads the result (`{"session_id", "cwd"}`) back from the temp JSON file (the child inherits `CLAUDE_CONFIG_DIR`, so it lists the same account). On POSIX it still runs in-process when stdin is a real tty, else prints a "needs an interactive terminal" note.

  **tray_minimizer integration (one-command `orch2.bat` workflow).** The normal launch runs the server *under* `tray_minimizer.py`, which hides the server's console to the tray. The picker's fresh `CREATE_NEW_CONSOLE` window would be a candidate for hiding too, so the picker **marks its window "no-hide"**: `copy_session.py` calls `SetConsoleTitleW("[nohide] orchestrator2 session picker")` *before* the slow `textual` import, and `LaunchPickerApp.TITLE` also starts with `[nohide]` so the marker survives Textual taking over the terminal title. `tray_minimizer.py` gained a `NO_HIDE_TITLE_PREFIX = "[nohide]"` constant and a `_title_is_no_hide(hwnd)` guard checked at its single hide chokepoint (`_hide_window`), in all three launch-mode detection strategies (so a marked window never counts as "the launched window"), and in the watch-mode event hook — so any window whose title starts with the prefix is left visible. Net effect: the picker appears in its own visible window while the orchestrator2 server sits hidden in the tray, and once the user picks (the picker process exits) the server proceeds to serve — the whole thing stays a single `orch2.bat`-style command even with `--copy`/`--resume`. *(orchestrator2/copy_session.py, trayminimizer/tray_minimizer.py)* The resolved id replaces `config.resume`. For `--detach`, the visible **parent** runs the picker and passes the resolved `--resume <id>` to the headless child via the rebuilt argv (stripping the original `--copy`/`--resume`). A cancelled resume-picker leaves the sentinel so the browser picker still appears. For `--copy`, once the copy is made **into the current account** the wizard asks "Open it now?" — **Yes** resumes the copy, **No** exits without opening; a cross-account copy shows a `NoticeScreen` (unresumable here). In every case where nothing was chosen to open (declined, cross-account, or cancelled anywhere in the wizard), the picker now presents a **"what to open?" fallback** (`FallbackOpenScreen`): **Open last** (the launch cwd's most-recent session — the Enter default, shown with its title), **Choose a session…** (the full project tree), or **Fresh session** (Esc). This avoids the earlier "I cancelled --copy but it loaded some *other* session in a new tab" surprise — nothing loads unless you say so, and the previous auto-continue behaviour is now the explicit default option. To compute the default, the server passes its launch `--cwd` to the picker child (`copy_session.py --pick <mode> --cwd <dir>`) and `_find_recent_for_cwd` finds the newest session under that cwd's project slug in the current account. Choosing **Fresh** leaves `chosen_id` unset, so `server.py`'s `main()` starts empty (`no_continue=True`). Verified with `Pilot` (resume mode returns the id; copy mode copies into the current account and returns the id) and `--copy`/`--resume` arg parsing. *(config.py, copy_session.py, server.py)*

- [x] **7. Stuck-on-"connecting" hang + auto-retry** — `bridge.connect()` awaited `self.client.connect()` with **no timeout**; when the Claude CLI spawns but never completes its init handshake, that call blocks forever, `state.connecting` stays `True`, and the UI shows "connecting (Ns)" indefinitely (observed ~700s). Fixed: the connect is now wrapped in `asyncio.wait_for(..., timeout=CONNECT_TIMEOUT=45s)`; on timeout/failure the half-open client is torn down (`disconnect()` + `self.client=None`) and the exception propagates to `worker_loop`'s existing connect-retry loop (10 attempts, exponential backoff), so a fresh spawn is attempted automatically — matching the user's observation that "trying again would probably connect." *(sdk_bridge.py)*

## Item #6 — findings & open question

Root cause of "doesn't share": conversations live under `<CLAUDE_CONFIG_DIR>/projects/<cwd>/`, so `claude --continue`/`--resume` only see a session when they use the **same** config dir. The user's setup:
- orchestrator2 runs under `CLAUDE_CONFIG_DIR = ~/.claude-account-c` (intended).
- Plain `claude` code is run under the **default** `~/.claude`.

Those are different accounts, so their histories are naturally separate. Claude Code's `--resume` enrichment does **not** filter out SDK (`sdk-py`) sessions (only `isSidechain` / `teamName` are excluded), so the session *format* is fine — it's purely the config-dir/account split.

**Open question for the user:** how do you want sharing to work? Options: (a) run plain `claude` with `CLAUDE_CONFIG_DIR=…\.claude-account-c` (or `--config-dir`equivalent) so it matches orchestrator2; (b) point orchestrator2 at `~/.claude`; (c) something else. Pending an answer, no code change is made here.
